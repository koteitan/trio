# BMS -> DBMS 変換の調査メモ

対象: BM4-Analysis-2021.4.27.xlsx シート `To psi(I)` の A 列(BMS) / E 列(DBMS)、1638 行。

## 0. DBMS とは（yaBMS c/bms.c の実装から）

**展開規則は BM4 と完全に同一。違うのは標準形判定の「対角」だけ。**

| | 対角 diag[x][y] |
|---|---|
| BMS (BM4) | `x` |
| DBMS | `max(x-y, 0)` |

つまり DBMS の対角は `(0)(1)(2,1)(3,2,1)(4,3,2)(5,4,3)...`（末尾 0 は省略記法）で、
行 y は列 y からしか立ち上がれない。3 行版 (DTSS) の対角は
`(0,0,0)(1,0,0)(2,1,0)(3,2,1)(4,3,2)(5,4,3)...(k,k-1,k-2)`。

出典は Ecl1psed 氏の Discord 発言 (2019) のみ。一次資料はローカルに無い（trio-agent 調べ）。

## 1. 実測でわかったこと

### (a) 行数は保存される
シートの 1638 対で、BMS が n 行なら DBMS も n 行（n=1:28, 2:236, 3:1373）。
つまり **TSS (3 行 BM4) ⇔ DTSS (3 行 DBMS)** で閉じている。

### (b) シートの検算
自作エンジン (`core.py`) で全 1638 対を標準形判定すると、
BMS 側 15 行 / DBMS 側 4 行が非標準形。うち数件は明らかな誤記
（`(3,20)`, `(3,32,1)`）。行 1098-1100 は両側とも非標準で、シート側の誤りらしい。
残り 1622 対を「使える対」として採点に用いる。

### (c) ord は展開規則だけで決まる（システム非依存）
行列 M の表す順序数は
```
ord(空) = 0
ord(M)  = ord(M-末尾列) + 1        (末尾列が全零)
ord(M)  = sup_n ord(M[n])          (それ以外)
```
で決まり、この定義に「BMS か DBMS か」は一切現れない。展開規則が共通だからである。
系として:

* **変換 f は「同じ順序数を表す DBMS 標準形を返す」写像**（＝標準形集合の順序同型）。
* **M が既に DBMS 標準形なら f(M) = M**（恒等）。
  実測: シートで DBMS 標準形でもある BMS 行列は 29 個（＝1 行行列）で、
  そのすべてで A 列 = E 列 ✅。

### (d) f は「行 0 の根」での分解について加法的
行 0 の値が 0 の列で区切ったブロック（＝順序数の和の項）ごとに変換して連結してよい。
```
f((0,0)(1,1)(0,0)) = f((0,0)(1,1)) ++ f((0,0)) = (0)(1)(2,1) ++ (0)
```
1622 対すべてでこの分解と矛盾しない。

### (e) 列数は保存されない（基本列がずれる）
```
BMS  (0,0)(1,1)(1,0)(2,1)(2,0)   = e0^w   (5 列)
DBMS (0)(1)(2,1)(2)              = e0^w   (4 列)
```
基本列は BMS 側が `e0^2, e0^3, ...`、DBMS 側が `e0, e0^2, ...` で **添字が 1 ずれる**。
DBMS の e0 = `(0)(1)(2,1)` が既に「コピー単位 (1,0)(2,1) を 1 個含む」形だから。
このため「展開アドレス（対角からのブラケット列）をそのまま再生する」方式は失敗する。

長さの差 len(DBMS)-len(BMS) の分布（1622 対）:
`-6:1, -5:11, -4:25, -3:82, -2:113, -1:99, 0:49, +1:216, +2:992, +3:27, +4:6, +6:1`

## 2. 素朴な構文規則 R1 / R2（`rule.py`）

**R1**: 先頭に DBMS 対角の長さ Y-1 の接頭辞を付け、各列を
`(a_0,...,a_{Y-1}) -> (a_0+(Y-1), a_1+(Y-2), ..., a_{Y-1}+0)` にずらす。
（BMS の `(0^Y)(1^Y)` が DBMS の `(0)(1)(2,1)...` に対応することから。）

**R2**: R1 をブロック（(d) の和の項）ごとに適用。

| 規則 | 正解数 / 1622 |
|---|---|
| R1 | 827 (51%) — Y=2 で 187/236 (79%)、Y=3 で 611/1357 (45%) |
| R2 | 835 (51%) |

**どちらも規則としては不正解**。長さが保存されないケース ((e)) を原理的に扱えない。

## 3. 正しい変換器 `convert.py`（原理は正しいが計算量が爆発する）

(c) から
```
f(0) = 空,  f(a+1) = f(a) ++ 全零列,  f(lim a) = sup_n f(a[n])
```
sup は「すべての f(a[n]) より大きい最小の DBMS 標準形」で、DBMS 対角から展開で降りて求める。
高速化: (c) の恒等ショートカット、(d) の加法性、基本列の接頭辞単調性を使った比較の早期確定。

小さい例（e0, e0*w, e0^2, z0, psi(W_2), psi(W_w) など）は正しく求まるが、
再帰が f(a[n]) を複数個要求するため深さについて指数的で、e0^w 以上で予算切れになる。

## 4. 本命の構文規則 R7 / R8（`rule.py`）

**BMS の 1 列が DBMS では「階段」になる**のが本質:
```
(1,1)   -> (1,0)(2,1)
(1,1,1) -> (1,0,0)(2,1,0)(3,2,1)
(2,1,1) -> (2,1,0)(3,2,1)     ← 階段の根 (1,0,0) が直前の列の像と共有されるので短い
(2,1)   -> (2,1)              ← 同上（直前が (1,0)）
```

### R7「影つき階段」
DBMS では、行 y (y>=1) の親になる列は「行 y-1 で 1 段深い**影**」でなければならない。
足りなければ影の列を挿入する（親ごとに 1 回だけ。以後は使い回す ＝ 階段の共有）。

```
shadow(p, 0) = img[p]
shadow(p, y) = shadow(p, y-1)                              … 行 y-1 の値が 1 以上なら
             = 新列 shadow(p,y-1) の行 0..y-1 に +1 を挿入   … さもなくば
T[y] = out[shadow(P_y(x), y)][y] + 1        (1 <= y <= t)
T[0] = max(out[img[P_0(x)]][0], out[shadow(P_t(x), t)][0]) + 1
```
（t = 列 x の最上位の非零行、P_y は BM4 の行 y の親。）

### R8 = R7 + コピー縮約
R7 の出力は順序数は合っているが**コピーが 1 個多い非標準形**になることがある
（§1(e) の添字ずれ）。そこで「良い部分の末尾がバッド部のコピー 1 個ぶんなら落とす」
縮約を、接頭辞ごとに標準形になるまで繰り返す。健全性の判定は
`expand(Z_red, n+1) == expand(Z, n)`（両者の sup が一致 ＝ 順序数不変）。

```
BMS  (0,0)(1,1)(1,0)(2,1)(2,0)
 R7  (0)(1)(2,1)(1)(2,1)(2)      ← 順序数は e0^w だが DBMS 非標準形
 R8  (0)(1)(2,1)(2)              ← 正解
```

### 採点（シートの使える 1622 対）

| 規則 | 合計 | Y=1 (28) | Y=2 (236) | Y=3 (1357) |
|---|---|---|---|---|
| R1（素朴なずらし） | 827 | 28 | 187 | 611 |
| R2（R1 をブロックごと） | 835 | 28 | ? | ? |
| R7（影つき階段のみ） | 330 | 28 | 215 | 86 |
| **R8（R7 + コピー縮約）** | **352** | 28 | **234 (99.2%)** | 89 (6.6%) |

**2 行（ペア数列）は R8 でほぼ解けた（234/236）。3 行はまだ。**

R1 の合計が大きいのは Y=3 で「たまたま当たる」形が多いだけで、規則としては R8 が正しい方向。

### 3 行で落ちる理由（診断）
縮約 `reduce_once` は「行列全体のバッドルートの直前」しか見ていないので、
入れ子になったコピーを落とせない。例:
```
BMS  (0,0,0)(1,1,1)(1,1,0)(2,2,1)(2,1,0)          5 列
true (0)(1)(2,1)(3,2,1)(3,1)                      5 列   ← (1,1,0)(2,2,1) が丸ごと吸収される
R8   (0)(1)(2,1)(3,2,1)(2,1)(3,2,1)(3,1)          7 列
```
trio-agent の測定（`~/proofs/trio/tmp/probe_bms2dbms_prefix.py`）とも整合:

* f は後続列について厳密（17/17 で `f(M)[:-1] == f(M[:-1])`）
* 列接頭辞 8940 組のうち **93.9% は「像の最後の 1 列を除いて接頭辞」**
  ＝ f は先読み 1 列の左→右トランスデューサでほぼ書ける
* 食い違う最後の 1 列はほぼ**持ち上げ**（差分 (0,1,0) が 2001 件 ＝ 行 1 が +1）
  「そこで行列が終わるなら低く、後ろに何か続くなら 1 段上げる」
* 残り 6.1% (548 組) が上の**吸収**。A_pre がコピー標識の途中で終わるときだけ起きる

### R9 / R10（事後縮約の拡張）— 失敗、原因も判明
逐語重複 `Z[i-L:i] == Z[i:i+L]` を 1 個落とす一般の縮約を、
共終性 `{Z[n]}` と `{Z_red[m]}` の相互共終で健全性判定するようにしてみた（`normalize2/3`）。

**うまくいかない。理由: cmpmat は非標準形に対して信用できない。**
```
Z  = (0)(1)(2,1)(1)(2,1)(2)(3,1)   ← R7 の出力（非標準形）
c  = (0)(1)(2,1)(2)(3,1)           ← 正解
expand(Z,1) = (0)(1)(2,1)(1)(2,1)(2)   … 順序数は e0^w だが非標準形
expand(c,1) = (0)(1)(2,1)(2)           … 同じ e0^w の標準形
cmpmat では前者 < 後者 と出る（先頭 7 番目が 1 vs 2）ので共終性判定が落ちる
```
つまり**書いてから消す方式は原理的に苦しい**。trio-agent の言う通り、
「そもそも書かない（被覆）」側で直すのが正しい。

### 次の一手
0. **被覆を直す（最優先）**。`shadow(p, y)` は親ごとにしか数えていないので、
   「いま書いている像そのもの」が既に階段の頭を与えている場合を数え落とす。
   trio の `~/proofs/trio/tools/probe_eps_range.py` `write_level` L234-268 の方式
   （候補の梯子たちと base の共通接頭辞を取り、その中の最深のレベル列まで被覆、
   持ち上げ `bump = d - lev` は行 1 値が相対的な列だけに掛ける）に差し替える。
1. 縮約を「無条件」ではなく「後ろに何か続くときだけ」にする（先読み 1 列で判定）。
2. 影の挿入を「親ごとに 1 回」ではなく trio の**梯子の被覆**方式にする
   （候補の梯子と共通接頭辞を取り、最深のレベル列まで、深さ d で頭打ち）。
   Y=3 で 86/1357 まで落ちるのは「手前で別目的に使われた階段の段」を数え落とす症状。
3. 検算をもう 1 本: `cmpmat` はバージョン非依存なので、シートの隣接行の大小が
   A 列と E 列で一致するはず（f が順序同型なら必ず成立）。自分の出力にも掛けられる。
